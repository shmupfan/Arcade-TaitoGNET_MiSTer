# MN10200 (MN1020012A) RTL: status

Status: M3 step 1, CPU core and the peripherals the Zoom firmware uses, in
RTL and verified against MAME 0.288 instruction by instruction
(2026-10-05). First fit measured, area trims done and re-verified, refit
pending; not yet connected to the Zoom block. Design:
docs/mn10200_design.md. Own code throughout: I wrote it from the design
study, the Panasonic manuals and MAME's behaviour; nothing is taken from
XelaNotPu's FX-1B core (I did not open it).

## 1. Summary

- `rtl/zoom/`: SystemVerilog, 5 modules, about 1,240 lines plus two
  generated ROM images. All 159 instruction forms of the design study
  (MN102L table plus F1:00 and F1:80) are implemented; an undefined opcode
  raises a simulation `$error` and then behaves as MAME (NMICR bit 1).
- Verification: a Verilator lockstep testbench compares PC, D0-D3, A0-A3,
  PSW, MDR, the cycle count of every instruction, the timer and pin
  interrupt request registers (FC42, FC50) and every external bus access
  with a MAME 0.288 debugger trace of `:taito_zoom:mn10200`.
- Result: 270.4 million instructions equal to MAME over four runs, each
  to the end of the run (section 4.2): the directed test of all 159 forms,
  psyvaria for 7 s and for 60 s of MAME time (attract, a credit and play)
  and raycris for 50 s (the other code variant); the game runs include
  the reset from the main CPU.
- First divergence: psyvaria instruction 35,659,552, MULU NF (section 4.3). MAME is wrong by the MN102L
  manual p.79; the core follows the manual. The testbench accepts this one
  case, counts it and continues.
- Speed: 7.52 to 8.74 FPGA clocks per instruction on the firmware with a
  zero-wait bus, against 11.27 available on average at 33.8688 MHz
  (design study 5.2). With the pacer on (psyvaria 7 s), the machine-cycle
  clock holds 6.2457 MHz (target 6.25). With one wait clock per bus access
  it falls to 5.91 MHz, which would slow the 1 kHz sound tick by about 5%: the Zoom glue
  must answer in the next clock (open item 2).
- Area: the first fit measured 2,302 ALMs needed, of which 217 are lost
  to the fit revision's virtual pins, so 2,085 for the MN10200 itself;
  1,431 registers, 3 M10K, 0 DSP, timing met (section 5.1). After the
  trims of section 5.2 (MLAB register file, one address adder, shared
  prescalers, word-wide register read) I expect about 1,700 ALMs; the
  refit is pending (section 6). The traces above were rerun on the trimmed
  core with the MAME-exact timer option.

## 3. What is implemented

### 3.1 CPU

- Multi-cycle sequencer: FETCH (with the interrupt sample at its end),
  EXEC, MEM, MD (multiply/divide), RET. The next instruction is fetched and
  decoded while the peripheral block steps the previous instruction's
  machine cycles (`mn10200_core.sv:375`).
- Fetch: one-word buffer plus one prefetch word (the word after the
  current instruction, read while the core waits at the boundary), bytes
  taken from the bus word on the ack clock, up to two bytes per clock;
  instruction length from the first byte only (`len_of`,
  `mn10200_core.sv:113`, design study 2.2).
- Decode: two synchronous ROMs as in design study 5.3, generated from the
  form table; 168 distinct control words (kind, addressing mode, width,
  sign extension, register files, B operand, immediate type, ALU function,
  flag class, writeback, branch condition, cycles, length). Register
  fields come straight from the key byte (bits 1:0, 3:2, 5:4).
- Register file D0-D3/A0-A3, 24-bit, in four MLAB copies with one write
  port, written the clock after the request (no state reads a register in
  the clock after writing it), cleared after reset by eight writes (MAME
  resets them to 0); A3 is read through the An port in the stack states.
- One address adder for effective addresses, branch targets, the stack
  steps and the second word of 24-bit accesses.
- One 25-bit adder for the ALU with the 16 and 24-bit flag sets from one
  operation (`mn10200_core.sv:230`); ADDC/SUBC keep ZF sticky (MN102L
  manual p.71); logic and shift forms on bits 15:0 with 23:16 kept.
- MUL/MULU: 16-step shift-add, signed last step subtracts; DIVU: 16-step
  restoring division, overflow (including divide by 0) detected up front
  as MDR >= divisor, which is exactly quotient >= 0x10000 (MN102L manual
  p.80).
- Bus: 16-bit, little-endian, byte enables, request held until ack; 24-bit
  accesses are a word then a byte at +2, 16 and 24-bit accesses are forced
  even as in MAME (design study O10). Internal I/O 0xFC00-0xFFFF is
  decoded inside and takes one clock.
- Interrupt entry: PC (24 bits) at A3-4, PSW at A3-6, A3 -= 6,
  PC = 0x080008, PSW IE cleared, IM = level, IAGR = group, 7 cycles.
- Cycle counting: each instruction retires the manual's minimum cycles
  (design study 2.4, the counts MAME charges); a taken branch adds 1;
  interrupt entry adds 7 to the next instruction's retire.
- Trace port: instruction start pulse with PC, registers, PSW, MDR and the
  cycle count (`DEBUG = 0` drops the 48-bit counter).

### 3.2 Peripherals

- Interrupt controller as MAME's model (design study 4.2): ten groups,
  request bits, enables and levels, the priority scan (lowest level below
  IM, ties to the lowest group), NMICR, IAGR read as group x 2.
- MAME's `m_possible_irq` behaviour is kept as a flag: interrupts are
  sampled only after an event that MAME marks (peripheral request, ICRH
  write, FC50/FC56 writes, RTI, MOV Dn,PSW, OR imm16,PSW, undefined
  opcode), never on AND imm16,PSW, and not before the first instruction of
  a handler (`mn10200.cpp:556-567`). A real chip probably samples the
  level every instruction; with the firmware's settings both give the same
  result as far as the traces reach (open item 7.5).
- EXTMD and the four IRQ pins: level and edge modes, P4 readback in FC57,
  re-sample on the FC50 acknowledge and on EXTMD writes.
- Timers 0-9, two options (`TIMER_EXACT`). 1: MAME-exact period
  (prescaler base + 1) x (cur + 1) machine cycles from arming
  (`mn10200.cpp:434`), with a per-timer prescale counter and the prescaler
  base latched at arming. 0 (build default): two shared prescalers that
  count every machine cycle, as on the chip; same periods, the first
  period after arming differs by up to the prescaler base. Both: cascade as
  `timer_tick_simple` (the low timer reloads to 0xFF until the high one
  underflows), re-arm on expiry with the new value, refresh of one timer on
  a mode write and of all on a prescaler mode write.
- Arming lands at the end of the writing instruction in machine time,
  because every cycle charge in `mn10200.cpp` precedes the memory access;
  the timer is frozen until then (deferred arming in `mn10200_periph.sv`).
- Ports 0-3 output, direction and input registers (port reads OR the
  direction bits as MAME does), port output strobes for the Zoom glue
  (port 1: TMS57002 PLOAD/CLOAD), pull-up registers, port 3 mode, serial
  0/1 control registers, serial 0 receive counter and status as MAME, CPUM
  stored (STOP/HALT not acted on, design study O4).
- Everything else (DMA, A/D, 16-bit timers, sync output, DRAM refresh)
  reads 0 and ignores writes. The firmware only initialises these.

### 3.3 Pacer

Credit accumulator, +15,625 per clock and -84,672 per machine cycle
(6,250,000 / 33,868,800 reduced exactly), capped at 64 cycles; the core
starts an instruction only with positive credit.

## 4. Verification

### 4.1 Method

- MAME 0.288 runs the game with `-debug -debugger none` and
  `mn102_oracle.lua`, which traces `:taito_zoom:mn10200` with a tracelog
  action (PC, D0-D3, A0-A3, PSW, MDR, `totalcycles`, FC57, FC50, FC42 before
  each instruction) and taps the external devices (ZSG-2, TMS57002,
  mailbox) into the same stream. Landmine: tracelog evaluates its symbols
  in the debugger's visible CPU; without `focus` the main CPU stays visible
  and the action prints nothing (comment in the Lua).
- The testbench loads the same `zoomprog` flash file, keeps the 128 KB RAM
  model across resets, and per instruction drives the inputs from MAME by
  instruction index: IRQ pin levels from FC57, the IRQ0 doorbell pulse when
  MAME shows the IRQ0 request and the core does not, external read data
  from the `B` lines, and a CPU reset where MAME restarts at 0x080000.
  External writes are checked against the `B` lines.
- One MAME at a time under nice -n 15 (the oracle refuses to start with 3
  MAME processes running); the testbench under nice -n 15.

### 4.2 Results

| Run | Instructions equal to MAME | Resets | IRQ0 pulses injected | External accesses checked | MULU NF accepted | FPGA clocks per instruction (0 waits) |
|---|---|---|---|---|---|---|
| Directed test (`mn102_testgen.py`, 4,000 steps, seed 1), in psyvaria's NVRAM set | 136,236 (whole first run) | 0 | 0 | 0 | 8 | 6.21 |
| psyvaria, 7 s, no input | 5,790,807 (whole run) | 1 | 0 | 4,137 | 0 | 7.52 |
| psyvaria, 60 s, coin at 20 s, start, fire, moves | 162,017,391 (whole run) | 1 | 7 | 1,495,602 | 94,671 | 8.74 |
| raycris (code variant A), 50 s, coin at 24 s | 102,436,392 (whole run) | 1 | 6 | 915,054 | 37,609 | 8.70 |

Every run ended at the MAME time limit with no divergence other than the
accepted MULU NF case. All four runs were repeated on the trimmed core
(commit c8ad6a7, `TIMER_EXACT = 1`) with the same counts. Compared per instruction: PC, D0-D3, A0-A3, PSW,
MDR, cycles of the previous instruction (including the 7 of interrupt
entry), FC42 (timer 0-3 requests, so the timer cascade and 1 kHz tick land
on the same instruction as MAME) and FC50 (pin requests); per access:
address, lanes and write data of every ZSG-2, TMS57002 and mailbox access.

The firmware runs executed 91 forms in the first 7 s; the directed test
executes all 159 about 25 times each with random register fields, corner
operands and random flags, which covers the forms the games never reach.

Clocks per instruction count the testbench's extra clock where a pin
changes. Bus wait sensitivity, directed test: 6.21, 8.94, 10.83 clocks per
instruction at 0, 1, 2 wait clocks per access. Pacer, psyvaria 7 s:
6.2457 MHz at 0 waits, 5.9099 MHz at 1 wait (the 7 s section averages
1.65 cycles per instruction, so it needs 8.96 clocks per instruction or
fewer).

### 4.3 First divergence: MULU NF (MAME)

At instruction 35,659,552 of the psyvaria run (`mulu d0,d1` at 0x0803FC,
product 0xBFFF4000) MAME leaves NF clear and the core sets it. MN102L
manual p.79 (MULU): "NF: Set if MSB of result (32 bits) is 1". MAME
computes `((uint16_t)a) * ((uint16_t)b)` (`mn10200.cpp:1142`), which C
promotes to signed int; a product of 2^31 or more overflows int, the
compiler may assume that cannot happen, and the `res & 0x80000000` test at
line 1145 never fires in the 0.288 binary I ran. MDR = 0xBFFF in the same
MAME line shows bit 31 of the product is 1. The core is right by the
manual; MAME is wrong. The testbench copies MAME's PSW into the core when
the only difference after a MULU is NF set in the core, counts it, and
goes on (`MN102_STRICT=1` turns this off).

With `MN102_STRICT=1` this MULU case is the first divergence in psyvaria
(instruction 35,659,552); after accepting it, none in the runs above.

### 4.4 Corrections to the design study found on the way

- Interrupt acceptance clears PSW.IE in MAME too: `take_irq` computes
  `(m_psw & 0xf0ff) | (level << 8)` (`mn10200.cpp:300`), and 0xF0FF clears
  bit 11. Design study 3.4 and O12 said MAME keeps IE (now corrected there). The MN102H manual
  agrees with clearing it (p.88: "IE = 0 unless the IE flag is set" during
  interrupt servicing). The core clears IE; my first build kept it and
  diverged at the first interrupt.
- BRA charges 2 cycles in MAME (1 for the opcode, 1 in `do_branch`), the
  table's taken count; the ROM generator had added the taken cycle on top.

### 4.5 Shared prescalers (TIMER_EXACT = 0) against MAME

- First difference: psyvaria instruction 3,962, FC42 bit 5 (timer 1
  request) set in the core and not yet in MAME. Timer 1 is the high half
  of the t1:t0 pair on prescaler 1 (base 7); its interrupt is not enabled,
  so only the request latch moves, by up to 7 machine cycles of phase.
- With the FC42/FC50 compare off (`MN102_NO_ICR=1`), psyvaria 60 s with
  play still matches MAME in every other respect for the whole run:
  162,017,391 instructions, same PC, registers, PSW, MDR, cycle counts,
  1,495,602 external accesses, 94,671 accepted MULU NF cases. The 1 kHz
  tick (t3:t2 on prescaler 0, base 0) is entered at the same instruction
  as in MAME, because with base 0 the shared prescaler ticks every cycle
  just as MAME's per-timer phase does.
- So for this firmware the shared prescalers change only when the
  unused timer request bits latch, not what the program does.

## 5. Area

### 5.1 First fit (measured)

Revision `MN10200_FIT` of the first version (before the trims below),
fitted on 2026-10-05 (`builds/20261005_1047_mn102`, not committed,
`MN10200_FIT.fit.rpt`, `.map.rpt`, `.sta.rpt`), per
`tools/fit_entities.py --node 'mn10200$'`:

| Entity | ALMs needed | ALUTs | Registers | M10K |
|---|---|---|---|---|
| mn10200 total | 2,302.0 | 3,311 | 1,431 | 3 |
| own logic (pacer, virtual pin cells) | 261.5 | 91 | 26 | 0 |
| mn10200_core (with the decode ROMs) | 1,153.6 | 1,757 | 639 | 3 |
| mn10200_periph | 886.9 | 1,463 | 766 | 0 |

0 DSP. Timing met at 29.525 ns: worst setup slack 6.963 ns (slow
1100 mV -40 C model), worst hold slack 0.151 ns (fast 1100 mV -40 C
model), from `MN10200_FIT.sta.summary`.

Where the own-logic figure comes from: the fit report puts 217 of its
261.5 ALMs under "ALMs unavailable, due to virtual I/Os" (434 virtual
pins; fit report, Fitter Resource Usage Summary); the logic placed at the
top is 44.5 ALMs (the pacer). In the G-NET build there are no virtual
pins, so the MN10200 itself measured 2,302 - 217 = 2,085 ALMs.

Where core and periph went over my paper estimate (section 5 of the first
version: 1,050 to 1,550): the register file in flip-flops with four read
multiplexers and eight write sources, eight separate 24-bit adders for
addresses, branch targets and stack steps, and in the periph the 20
per-timer prescale counters and latched bases (480 timer registers in
all) plus two independent byte-wide read decoders.

### 5.2 Trims (same behaviour, re-verified)

| Change | Where | Expected effect (estimate, not fitted) |
|---|---|---|
| Register file in four MLAB copies, one write port written the clock after the request, cleared after reset by a write sequence (S_CLR); A3 read through the An port | `mn10200_rf.sv`, `RF_MLAB = 1` | 192 registers and the read multiplexers replaced by 8 MLABs; about 100 ALMs |
| One address adder (AGU) for effective addresses, branch targets, A3 - 4 / - 6 / + 2 / + 4 / + 6 and the second word of 24-bit accesses; next PC from the fetch position; JSR pushes in its own state | `mn10200_core.sv` | eight 24-bit adders less, operand multiplexers more; about 80 ALMs |
| One adder for the multiply step (add or subtract) | `mn10200_core.sv` | about 10 ALMs |
| Shared prescalers (TIMER_EXACT = 0, the build default) | `mn10200_periph.sv` | 160 registers and 20 8-bit counters less; about 150 ALMs |
| Register read decoded once per 16-bit word | `mn10200_periph.sv` | about 30 ALMs |
| Pacer: one adder with a constant operand | `mn10200.sv` | about 10 ALMs |

My expectation for the refit: about 1,700 ALMs for the MN10200 itself,
plus the virtual-pin share the fitter reports, so the "ALMs needed" line
of `MN10200_FIT` should land near 1,900. The MLAB inference needs
checking in the refit: the map report's RAM summary should list four
MLAB RAMs under `mn10200_rf`; if Quartus keeps the file in logic,
`RF_MLAB` falls back to the old cost.

TIMER_EXACT = 0 changes when the timers latch their requests; the
comparison against MAME is in 4.5. The trace verification builds use TIMER_EXACT = 1
(`sim/mn10200/build.sh` default).

## 6. Fit request

Revision `MN10200_FIT` (project `MN10200_FIT.qpf` in the repository root):
top `mn10200`, the five `rtl/zoom/*.sv` files, all ports except `clk` as
virtual pins, `DEBUG = 0`, `RF_MLAB = 1`, `TIMER_EXACT = 0`, clk

project directory.

## 7. Open items

1. Fit (section 6), then the gate of design study 5.10.
2. Bus latency: the core keeps real time at 33.8688 MHz only if program
   flash and work RAM answer in the next clock (BRAM program cache hit,
   BRAM work RAM). At one wait clock the pacer measured 5.91 MHz instead of
   6.25 on psyvaria. Options if the Zoom glue cannot do that: a deeper
   prefetch queue, or clocking the MN10200 from clk_2x with the same pacer
   (PACE_ADD and PACE_SUB change, behaviour does not).
3. Refit (section 6): check the MLAB inference of `mn10200_rf` and the
   per-unit figures against section 5.2.
4. Timers: which phase the MN1020012A really has (design study O7). The
   build default follows the chip family (shared prescalers); the
   MAME-exact option stays for trace comparison.
5. Interrupt sampling: kept as MAME's event flag for trace equality (decision
   2026-10-05: keep for now); the chip most likely samples the level every
   instruction (related to design study O12). Decide once the
   older-generation manual (O1) is found.
6. The verification aligns external inputs by instruction index. The real
   Zoom block will take IRQ0 and the TMS57002 FIFO line in real time
   (design study 7.2 and 7.3); M3 board-level checks still to do.
7. Undefined opcodes: NMI as MAME, not seen in any trace.
